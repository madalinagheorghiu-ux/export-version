1Problem & goals

Some operations are long-running (an export can take up to ~15 min; a bulk migration runs seconds-to-minutes). The user must be free to close the launching modal, navigate, refresh, or leave and come back — and still be told, reliably, when the operation changes state. A toast alone isn’t enough: it’s ephemeral and easily missed.

Reach the user anywhere

The indicator lives in the always-mounted app shell, not in the operation’s modal.

Never lose a notification

Persisted server-side, pushed in real time, pulled on reconnect.

Actionable

Each item carries the next step — download / view / review / retry — not just a status.

Extensible by type

One feed, many operation kinds, without a redesign per kind.

Unambiguous context

Every notification says where it belongs (environment / workspace / project, or organization).

No dedicated page

The panel is the home; per-item detail is surfaced in the operation’s own modals.

2The model: an async job whose state changes are the notifications

Every operation is modelled as a server-side job with a lifecycle. The notification is the messenger that announces a transition; the follow-up action (download / view / review / retry) is a separate interaction against the job’s result.

REQUESTED ──► IN PROGRESS ──► SUCCESS
                    │        └──► WARNING   (done-with-caveats, or needs-review-to-proceed)
                    └────────────► FAILED   (retryable)

Beyond in progress, every terminal notification resolves to exactly one of three statuses, which drive the icon, colour and CTA:

StatusMeaningIcon / colourDefault CTA
In progressRunning; not done yet.Spinner · neutral—
SuccessCompleted cleanly.Check · greenDownload or View
WarningTwo flavours — completed with warnings, or not completed yet but can proceed if the user accepts the impact.Triangle · amberReview or View
FailedDid not complete; can be retried.✕ · redRetry

3Operation types & notification titles

Seven long-running operations ride on this mechanism today. The naming convention:

  • Title = {subject} {outcome}. The subject stays identical across all statuses of a type; only the outcome word changes, so the same operation reads consistently as it moves success → warning → failed.
  • Counts, versions and names never go in the title — they belong in the subtitle. The one exception is the warning count (it is the point of the warning).
  • Two success verbs by category: operations that produce a file → “ready to download”; operations that apply a change → past participle (“imported” / “migrated”).
  • Status drives icon + colour + CTA; the title’s outcome word matches the status.

The warning status is really two flavours

They share the amber colour but differ in whether the operation finished, which changes the CTA:

  • W-a · needs review / accept impact (not finished — proceeds only if the user accepts) → types 1, 2, 3, 4 (and 7). Title: “ready — {N} excluded” / “needs review — {N} conflicts”. CTA = Review → then Download / Import.
  • W-b · completed with warnings (finished, with caveats) → types 5, 6. Title: “…ed — {N} skipped / failed”. CTA = View (details).

4Subtitle & CTA per status

The title carries type + outcome; the subtitle carries the specifics (what → where, counts), and the action carries the next step.

CTA styling rule

Feed & toast actions are secondary buttons with blue text. An icon appears only when the click downloads immediately (Download → ⬇). Anything that opens a step first (Review, View, Retry) is text-only — so the icon reliably means “one click = file in hand.”

5Notification center anatomy

Surface

A global bell in the dark app-shell header with an unread badge, always mounted and independent of any operation modal. Clicking it opens a contextual panel anchored under the bell. Live arrivals also raise a toast.

Panel layout (top → bottom)

  • Header — “Notifications” + Mark all as read (a text link; disabled, not hidden, when nothing is unread).
  • Search + a filter icon (§7) — the filter is an occasional control, so it collapses to an icon rather than a persistent row. The icon highlights when a filter is active; single-select, so there’s no filter chip.
  • Feed — one unified list, grouped by time into Today / This week / Older.
  • Footer — “Notifications are kept for 30 days.”

Feed item — two rows

  • Context row: environment badge (or organization area) · workspace · project · time. A mark-as-read ✓ appears on hover in a fixed slot before the time, so timestamps stay column-aligned across read and unread rows alike.
  • Status row: status glyph · title · subtitle · inline action.
  • Status glyph is deliberately discrete — a small colour-coded check / warning / ✕, not a filled tile — so a column of them stays calm rather than reading as a traffic light.
  • Unread is a blue left-accent bar (+ the header/badge count).

6Width & sizing

Recommended panel width: 420 px (min 380 / max 440, responsive; the panel scrolls internally, capped ~ 480 px tall).

Reasoning, benchmarked against contextual notification panels in comparable tools:

ProductSurfaceApprox. width
JiraHeader dropdown~400 px
NotionInbox side panel~420–460 px
SlackActivity panel~400 px
GitHubDropdown → links to a full page~370 px
LinearFull-page inbox + panelpage-width
  • Below ~360 px the two-row item (badge + workspace·project + time on row 1; glyph + title + subtitle + CTA on row 2) truncates and the CTA crowds.
  • Above ~480 px a bell-anchored dropdown starts to feel like it wants to be a page.
  • Because FlowX has no dedicated notifications page, the panel is the primary surface — so lean to the comfortable end (420, not 360).
  • Because per-item detail lives in the operation’s own modals (the excluded-resources panel, the migration detail page), the panel does not need to show everything — so it doesn’t need to grow into a page either. 420 px is the balance.

Toasts stay a touch narrower (~360 px) since they’re transient and single-action.

7Scope: organization vs environment type · filtering

An organization spans three environment types — PRODUCTION / STAGING / SANDBOX — plus the org itself. Every notification has one of two scopes:

  • Environment-type scope — work-in-an-environment kinds (export, import, migration). Stamped with { env, workspace, project }, shown with the colour-coded environment badge (blue Sandbox · amber Staging · dark Production).
  • Organization scope — org-wide events that belong to no single environment (e.g. Bulk Import End-Users, licence expiry, billing). Stamped with { area, target } and shown as a plain {area} · {target} line (e.g. Access Management · End-Users) — no coloured badge (the absence of an environment badge is itself the “not environment-specific” signal).

Filtering folds read-state and scope into one single-select popover off the filter icon:

All notifications
Unread (N)              ← read-state
────────────
Organization           ← org-level items
────────────
ENVIRONMENT TYPE
  Production / Staging / Sandbox

One active filter at a time; picking Unread shows unread across every scope. Trade-off: the two axes can’t currently be intersected (e.g. “unread Production”) — chosen for simplicity over a separate All/Unread toggle. Free-text search matches title + source label + context and composes with the filter.

8Toast (live arrival)

A toast is the same object as a feed item, just shorter-lived — it reuses the exact two-row structure, the discrete status glyph, the same colours and the same action rule (⬇ Download for a clean result, text-only Review / View otherwise). It carries only what’s needed and a status-matched left accent (green / amber / red). A toast showing fewer fields than the feed is expected.

Don’t double-surface

The governing rule: a toast fires only when the user ends up not looking at the finished result. Suppressed when the center is open; when the launching “Preparing… / In progress” modal for that job is still open (it switches straight to the result instead of toasting); and on a direct instant action on a cache hit — clicking Get download when an identical export is “available instantly” fires the download there and then, so no toast, and the entry lands already read. Conversely it does fire when the user backgrounds an op (Close — keep working) and it finishes while they’re away (§9).

Auto-dismiss & persistence

A toast lingers just long enough to read and reach for its action, then clears itself — but it never expires while the user is engaging with it or away from the tab. Each toast owns its own countdown, so they dismiss independently rather than as a batch.

  • Duration by weight — 5 s for a toast with no action; 7 s for one carrying a CTA (Download / Review / View), which needs the extra beat to be reached.
  • Paused (frozen, not reset) while the pointer is hovering the toast, keyboard focus is inside it, or the window/tab is blurred (visibilitychange — the user is in another tab or app). Holds can overlap; the countdown resumes only once all are released.
  • Resumes on mouse-leave / focus-out / window-focus, banking the time already elapsed.
  • A manual × dismisses immediately, regardless of the timer.
1000 ms grace on resume

On resume the remaining time is floored to 1 s, so a nearly-expired toast can’t vanish the instant the cursor or focus leaves it.

9In-progress: launch modal, bell pulse & the count

Long-running ops spend most of their life in progress. Four rules keep that phase honest.

The launch modal is a dismissible confirmation

Pressing a committing CTA (Start Migration, Export) opens a small “…in progress” modal modelled on export’s Preparing… screen: spinner, what → where, and a “Close — keep working” button. It exists to (a) confirm an irreversible action actually started, and (b) say “you can leave — we’ll notify you.”

Not a trap

Close it any time — a running op’s modal is never treated as dirty (§10), so leaving loses nothing. If left open through completion, it switches straight to the result (§8).

Not pure background

A bare toast is too ephemeral to be the only acknowledgement that a non-reversible op launched. The modal is the “it started” handshake; the toast/feed is the “it finished” one.

Minimum on-screen time — ~1 s

The launch modal stays up for at least ~1 second even if the op finishes near-instantly (cache hit, tiny migration), so it reads as “it started” instead of flashing (MIN_MODAL_MS). A floor, not a fixed wait — a genuinely long op is unaffected. This is the answer to the “quick migrations make the modal flash” caveat.

The bell pulses when the modal is backgrounded

Pressing Close — keep working fires a one-shot pulse on the header bell — the visual handshake tying the just-dismissed modal to where the operation now lives, answering “where do I check on this?” without words. Suppressed when the panel is already open (the user can already see the feed update).

The unread count never counts in-progress

The numeric badge means exactly one thing: unread terminal results that need you (ready / done / failed / org events). A pending entry has no action — counting it would cry wolf (open the bell, find only a spinner) and double-count at completion (does preparing → ready bump it a second time?). So in-progress shows in the feed (a spinner row — discoverable) but out of the count; “work is happening” is carried by the pulse + the live row, never a number.

Activity ≠ unread-actionable — the two signals are shown differently on purpose.

At completion, it hinges on one thing: is the user still looking?

  • Routed to the result (they let the modal switch them to the download / review / detail view) → they’re looking → no toast, and the entry is written already read — kept as history (30-day retention + cross-surface pull) without inflating the count or re-alerting. A record, not a second notification. (Mirrors export, which marks the job read when its Preparing modal switches to the download modal.)
  • Backgrounded it via Close — keep working → they’ve stopped looking → toast + unread, like any not-watched completion. This holds even in the min-display sliver — if the op finished during that ≤1 s hold and they click Close — keep working in it, they still get the toast, not a silent unread row. (A backgrounded-and-still-running op instead pulses the bell; the toast comes later when it completes.)

10Navigating from a notification

A notification never navigates on its own — every route is a user click. Acting on one that routes to a page can fire while a modal is open (a toast sits above the scrim) or from a config page (the bell is reachable there). If the user is mid-setup (a migration setup/config, or an export setup), a “Discard unsaved changes?” guard appears first — Keep working stays put and leaves the notification unread; Discard & leave tears the flow down and routes. A running operation’s progress modal is not treated as dirty (it keeps going in the background), and a plain download doesn’t navigate at all — so neither prompts.

Never stack a modal on a modal

When the dirty flow is itself a modal, the guard doesn’t open a second scrim on top — the underlying modal is hidden while the confirm shows (its state is preserved), so exactly one surface and one focus target exist at a time. Stacked modals are avoided on purpose (double-dimming + competing focus traps / Esc handling).

11Failure handling

A FAILED transition raises a notification like any other. For a system-outage failure the copy should: name the failure, reassure that nothing was applied (the main anxiety with a mid-run failure), and offer Retry. Keep the wording identical across toast, feed row, and detail page so it reads as one error, not three. A failed item shows no status chip — the red glyph + title already say it; the action slot holds Retry.

Example — bulk migration, service unavailable

Instance migration failed — the migration service is temporarily unavailable, so the operation couldn’t run. Your process instances weren’t changed. Retry once it’s back.

Only claim “nothing was changed” if the operation is transactional/atomic. If a partial effect is possible, soften to “Some items may not have been processed — open details to review before retrying.”

12Edge cases

  • Concurrent identical requests — cache key + job lock; the second request attaches to the in-flight job (one notification, not two).
  • Result expiry — clicking a stale notification shows “expired — re-run”, not a broken action.
  • Source changed after request — a content-revision in the cache key prevents reuse of a stale artifact (fresh run → fresh notification).
  • Permissions — re-checked at action time (download / view), not just at request time.
  • Multiple queued operations — each notification carries a job id + human label to stay distinguishable.
  • Retention — the center keeps the last 30 days; the footer states this so the absence of older items reads as policy, not loss.

13Future & open questions

Retry on failed

Wire the Retry action end-to-end (re-run the job from the notification).

Archive

Reintroduce per-item dismiss as an on-hover archive action, once there’s an archive destination.

Deep-link “Go to”

Jump to the build / version / project a notification refers to, auto-switching workspace + env.

Grouping by workspace

Time grouping ships today; workspace grouping is a candidate as volume grows.

Priority / severity

Errors and licence expiry styled distinctly, optionally pinned.

Preferences

Mute types, do-not-disturb, optional email/desktop for long-running jobs.

Open questions

  • Notification infra — reuse FlowX’s real-time/notification infrastructure vs. a dedicated path (recommend reuse; needs codebase confirmation).
  • Import warnings — do imports surface a pre-apply review (“N conflicts”, W-a), or auto-apply and report afterward (“imported — N skipped”, W-b)? This flips the titles for types 3–4.
  • Job cancelability — can an in-flight job be cancelled, or does it run to completion?
  • Artifact / result TTL — exact retention window and how expiry surfaces in the feed.
  • Per-user vs. shared — are notifications strictly per-user, or should a shared operation notify a team?
